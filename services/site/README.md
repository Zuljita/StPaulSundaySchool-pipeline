# The public site

Everything approved, rendered as web pages and served from R2. It is
public: no sign-in, no roster, nothing to log into. It installs to a
phone's home screen and reads without a signal.

**It holds no opinion about what may be published.** By the time a page
reaches this Worker, `build.py` has refused to render an unapproved
Sunday and `publish_site.py` has re-checked the hash and the approval.
This service maps a URL onto an R2 key.

---

## Why the site is a renderer and not an export

The app used to be a separate system the content was pushed into.
`fetch_app.py`, `drift.py` and `import_app.py` exist to measure how far
that second system drifted from the approved text, and the answer, once,
was that 5 of 12 pieces never arrived and none of the 7 that did matched
the print.

`tools/stpaul/render/site.py` runs in the same pass as the DOCX and the
PDF, over the same parse of the same bytes. There is no second derivation
left to drift. The hash in a page's colophon is the hash in the handout's
colophon because both came out of one call.

The Base44 export is still produced. It is a locked schema, it costs
almost nothing, and it is the bridge while the app is still running.

## How a Sunday reaches the internet

Normally nobody does this by hand. `.github/workflows/publish.yml` runs
the whole chain on a schedule, and again within about a minute of an
approval being recorded. By hand it is:

```powershell
$env:STPAUL_DATA = "D:\dev\StPaulSundaySchool"

python tools\make_review.py                   # new content becomes reviewable
python tools\build.py --all --approved-only   # builds what is approved
python tools\publish_site.py                  # re-checks, then stages
python tools\publish_r2.py --staged "D:\dev\StPaulSundaySchool\dist-site"
```

`publish_site.py` skips a Sunday, by name and with the reason, when it is
a draft build, when it was built unapproved, when the content has changed
since the build, or when the approval is no longer current. A stale build
is not published; it is rebuilt.

`--approved-only` passes over a Sunday still waiting on a pastor instead
of failing on it. Most of a year is waiting at any given moment, and that
is the normal state rather than an error. Without the flag, `build.py`
still refuses an unapproved Sunday outright.

## Installing it

The site is a progressive web app: Android offers "Add to Home Screen"
and it opens without a browser bar, which is what the Base44 app gives a
reader today. Chrome wants three things and all three are here.

| | |
|---|---|
| A manifest | `/manifest.webmanifest`, generated by `render/site.py` |
| Icons at 192 and 512, plain and maskable | cut from the church logo by `tools/make_icons.py` |
| A service worker | `/sw.js`, generated at publish time |

On iOS there is no install prompt; Safari's Share → Add to Home Screen
works, and the page carries the `apple-touch-icon` and title it needs.

**The icon is a crop, not a new mark.** The church logo is a horizontal
lockup, useless as a tile at 3751x686, but its rosette is exactly
686x686. Inventing an app icon would have been a design decision that
was not the pipeline's to make.

**Offline.** The worker caches the shell and the newest Sunday's pages at
install, and everything else as it is visited. Pages are network-first,
so a reader with signal always sees a republished Sunday and a reader
without one still gets the lesson. Handouts are never cached: a year of
PDFs would fill a phone, and downloading them is what a download is for.

**The cache is versioned by the content**, not by the clock. Keyed on
build time it would evict itself on every publish whether or not anything
changed; keyed on nothing it would serve last week's lesson forever.

## The whole week in one file

Every Sunday page links a ZIP holding all twelve PDFs, all twelve DOCX
and the plain-text handoff. `render/package.py` builds it in the same
pass, with fixed entry timestamps and a fixed `create_system`, so two
builds of the same approved bytes produce the same archive on Windows and
on Linux alike.

## Two things that deploy separately, on purpose

| | |
|---|---|
| **The Worker** | `.github/workflows/deploy-site.yml`, on a push to `main`. Needs no curriculum. |
| **The content** | `.github/workflows/publish.yml`, or `publish_r2.py` by hand. Needs no Worker deploy. |

That split is why this Worker reads from R2 instead of bundling static
assets. Bundled pages would have to be uploaded at deploy time, which
would mean this public repository's CI needed a checkout of the private
curriculum. Reading from R2 keeps the machinery publishable, the content
private, and lets the person who can approve a lesson publish it without
holding deploy credentials.

## Setup

Two steps, both needing Cloudflare access.

**1. Create the bucket.** The name must match `bucket_name` in
`wrangler.toml`.

```powershell
npx wrangler r2 bucket create stpaul-sundayschool
```

**2. Point a hostname at the Worker.** `wrangler.toml` has
`sundayschool.stpaulaustin.org`; the zone must be on Cloudflare DNS.

> **Not the approval service's hostname.**
>
> `schoolreview.stpaulaustin.org` is authorised on a Google OAuth client
> that decides who may approve doctrine, and an origin is a trust
> boundary. This site is public, has no sign-in and holds no credential,
> so co-hosting would gain nothing and would put a public page inside
> that boundary. Give it its own name.

**3. Set the repository secrets.**

| Secret | For | Scope |
|---|---|---|
| `CLOUDFLARE_API_TOKEN` | deploying and uploading | Edit Cloudflare Workers, **and** Workers R2 Storage: Edit |
| `CLOUDFLARE_ACCOUNT_ID` | both, if the token sees more than one account | |
| `DATA_REPO_TOKEN` | `publish.yml` reading the curriculum | Contents: read/write on the data repository only |

`DATA_REPO_TOKEN` needs write only so the publish workflow can commit
`review/data/`, which is generated from content and is what makes a newly
added Sunday visible to a reviewer. It writes nothing else.

**4. Optional: publish the moment a Sunday is approved.** Set
`PUBLISH_REPO` and the `PUBLISH_DISPATCH_TOKEN` secret on the approval
Worker and it fires this repository's publish workflow after recording an
approval. Leave them unset and nothing breaks: the workflow runs on a
schedule too, so an approval reaches the site either way. The dispatch is
written so it can never fail an approval.

## What the site is made of

One script, and it is the service worker registration. There is no
inline script and no event handler anywhere, so the Content-Security
Policy needs no `'unsafe-inline'` and forbids everything the page did not
load from this origin as a file. Every page renders completely with
JavaScript switched off; the worker only adds offline reading and the
install prompt. `test_site.py` fails if a second script appears, if one
becomes inline, or if the body starts depending on one.

Curriculum text is HTML-escaped when it is rendered, including the parts
that look like markup, because imported content has carried raw tags
before. `tools/tests/test_site.py` counts every `<` in the output and
fails on one the renderer did not write.

| URL | R2 key |
|---|---|
| `/` | `index.html` |
| `/<sunday>/` | `<sunday>/index.html` |
| `/<sunday>/pieces/05-primary-teacher-guide.html` | the same path |
| `/handouts/<sunday>/05-primary-teacher-guide.pdf` | the same path |
| `/handouts/<sunday>/<sunday>-package.zip` | the same path |
| `/assets/site.css`, `/manifest.webmanifest`, `/sw.js` | the same path |

The key is the URL path. A 404 is always a missing object, never a
rewrite rule disagreeing with another rewrite rule.
